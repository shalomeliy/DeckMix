# v0.9.56 — הגל קופץ בזמן ניתוח: מדידה, ותיקון של חלק אחד (07/10)

**הדיווח (שלום 07/10, אחרי v0.9.51–54):** הסאונד בסדר יותר, אבל הוויזואליזציה של הגל קופצת בזמן שהניתוח רץ אחרי פתיחת הדף.

**מה נמדד (Chromium headless בקונטיינר, 4 ליבות, סקריפטים זמניים — לא במחשב של שלום):** פער בין פריימים, כשהמסך אמור להתעדכן כל 17ms.
| מה רץ | הפער הגדול | פריימים מעל 50ms |
| --- | --- | --- |
| כלום | 17ms | 0 |
| hash, 4 קבצים במקביל (40×13MB) | 100–117ms | 8–12 |
| hash, קובץ אחד בכל פעם | 50–67ms | 0–1 (אותו זמן כולל) |
| פענוח MP3 של 5 דקות (`decodeAudioData`), 2 במקביל | 250–383ms | 4–5 ל-6 שירים |
| אותו פענוח, אחד בכל פעם | 50–67ms | כמעט אחד לכל שיר |
| עדכון שורה בספרייה של 343 שירים (React) | ~9ms | 0 |

**מסקנה:** כל פענוח של שיר מקפיא את המסך פעם אחת, כי Chromium בונה את ה-AudioBuffer על ה-main thread — גם כשהפענוח עצמו בחוט אחר,
וגם ב-OfflineAudioContext (נמדד). זה מה שנשאר אחרי v0.9.51. אין `decodeAudioData` ב-Worker.

**מה תוקן כאן:** מעבר ה-hash קורא קובץ אחד בכל פעם (`HASH_CONCURRENCY`, `tests/repo/hash-pass-one-at-a-time.test.ts`) — הקפאות הפתיחה
ירדו מ-~110ms לכ-50–60ms בלי להאריך את המעבר.

**מה פתוח (החלטה של שלום):** פענוח בתוך Worker עם מפענח קטן וחינמי (WASM, mp3/flac/ogg; wav ב-JS), כך שה-main thread לא נוגע בשיר
בכלל במעברי הרקע. m4a נשאר בדרך הישנה. זו גרסה בפני עצמה.
