# v0.8.29 — ז'אנר ידני לא נעלם בזמן ניתוח מחדש

**נסגרה 24/09.** דיווח שלום, מיד אחרי v0.8.27: "לכל השירים חסר הז'אנר שקודם היה להם".

## מה היה שבור

ז'אנר שנבחר ידנית (וגם הערה ו"נוגן לאחרונה") שמור לפי טביעת האצבע של הקובץ (`contentHash`), והיא
חושבה **בתוך** לולאת הניתוח — שיר חיכה מאחורי כל הפענוחים שלפניו. כל עוד המטמון ענה במילישניות זה לא
הורגש; כש-`ANALYZER_VERSION` 3 (v0.8.27) שלח את כל הספרייה לניתוח מחדש, הז'אנרים חזרו אחד-אחד לאורך
כל התור. שום דבר לא נמחק — רק לא הוצג.

## מה נעשה

`queueLibraryAnalysis` (`platform/source-fsaccess/library.ts`): מעבר ראשון מחשב hash לכל השירים
(4 במקביל, עדכונים באצוות), ורק אחריו הניתוח. הקובץ נקרא שוב רק בהחמצת מטמון — בטעינה רגילה (הכל
במטמון) נקרא פעם אחת, כמו קודם. כישלון hash עדיין מדווח ככישלון ניתוח של השיר, לא נבלע.

## מה נמדד

`scripts/verify-genre-before-analysis.mjs` — Chrome אמיתי, 8 mp3 אמיתיים מ-House (קריאה בלבד), לכולם
ז'אנר שמור: **אחרי התיקון כל השורות מראות אותו אחרי 1.9 שנ', כש-8/8 עוד בתור; לפני — 34 שנ', כשנשארו
3 בתור.** `verify-analysis-queue` 9/9, `verify-key-detect-wiring` 8/8, `npm run check` ירוק.

## סקירה עצמאית (`change-reviewer`) — PASS

- **נוסף:** קובץ שנעלם אחרי הסריקה (`getFile` נכשל כבר בשלב ה-hash) — `verify-analysis-queue` מכסה
  אותו עכשיו: נקודה כתומה עם הסיבה, לא נעלם בשקט.
- **נמדד:** hash לכל הספרייה (362 קבצים, 4.8GB) ~12 שנ' ב-Node. בזמן הזה השורות "queued" והז'אנרים
  מתמלאים בהדרגה (אצוות כל 300ms).
- **מחיר ידוע:** בהחמצת מטמון הקובץ נקרא פעמיים (hash, ואז פענוח). קובץ שמשתנה בין שתי הקריאות יישמר
  תחת ה-hash הישן — נדיר, והניתוח הבא מתקן.
